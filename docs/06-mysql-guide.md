## 1. Schema Design and Migrations

We use relational databases (MySQL) to store primary accounts and customers data. These structures require ACID transactional guarantees.

### SQL DDL (Data Definition Language)
Our tables enforce relational schemas, data types, primary and foreign keys:

*   **Primary Key Constraints:** Uniquely identify rows (e.g., `id BIGINT NOT NULL AUTO_INCREMENT`).
*   **Foreign Key Constraints:** Establish relationships between tables (e.g., linking `accounts.customer_id` to `customers.id`).
*   **Check Constraints:** Enforce business validations at the database layer (e.g., `chk_balance_non_negative CHECK (balance >= 0)`).

```sql
-- Example from V1__create_accounts_table.sql
CREATE TABLE IF NOT EXISTS accounts (
    id             BIGINT         NOT NULL AUTO_INCREMENT,
    customer_id    BIGINT         NOT NULL,
    account_number VARCHAR(20)    NOT NULL,
    account_type   ENUM('SAVINGS', 'CHECKING', 'INVESTMENT') NOT NULL,
    balance        DECIMAL(19, 4) NOT NULL DEFAULT 0.0000,
    currency       CHAR(3)        NOT NULL DEFAULT 'USD',
    status         ENUM('ACTIVE', 'INACTIVE', 'CLOSED', 'FROZEN') NOT NULL DEFAULT 'ACTIVE',
    
    CONSTRAINT pk_accounts         PRIMARY KEY (id),
    CONSTRAINT uq_accounts_number  UNIQUE (account_number),
    CONSTRAINT fk_accounts_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT chk_balance_non_negative CHECK (balance >= 0)
);
```

### Seeding in Docker Compose
To seed or initialize the database on startup, the migration SQL folder `./db/migration` is mounted into the MySQL container at `/docker-entrypoint-initdb.d`. MySQL automatically runs any `.sql` or `.sh` script placed here when the database container starts for the first time.

```yaml
# In docker-compose.yml
services:
  mysql:
    image: mysql:8.0
    volumes:
      - mysql-data:/var/lib/mysql
      - ./db/migration:/docker-entrypoint-initdb.d
```

## 2. JDBI 3 (SQL Object API) in Kotlin

JDBI is a SQL convenience library for Java/Kotlin. In this project, we use JDBI's **SQL Object API**, which maps Java interfaces directly to SQL statements via annotations.

### Declarative DAOs
You write abstract interfaces annotated with `@SqlQuery` or `@SqlUpdate`. JDBI automatically builds the dynamic implementations at runtime.

*   `@SqlQuery`: Used for queries that return data (SELECT).
*   `@SqlUpdate`: Used for operations that modify data (INSERT, UPDATE, DELETE).
*   `@Bind`: Binds a function parameter to a named parameter in the SQL query.
*   `@GetGeneratedKeys`: Automatically retrieves and returns the auto-increment ID generated by an INSERT statement.

```kotlin
// Example from AccountDao.kt
interface CustomerDao {

    @SqlUpdate("""
        INSERT INTO customers (first_name, last_name, email, status)
        VALUES (:firstName, :lastName, :email, :status)
    """)
    @GetGeneratedKeys("id")
    fun insert(
        @Bind("firstName") firstName: String,
        @Bind("lastName")  lastName: String,
        @Bind("email")     email: String,
        @Bind("status")    status: String
    ): Long

    @SqlQuery("SELECT * FROM customers WHERE id = :id")
    fun findById(@Bind("id") id: Long): Customer?
}
```

### Row Mappers
JDBI needs to know how to map SQL `ResultSet` rows to Kotlin objects. You do this by implementing JDBI's `RowMapper<T>` and registering it on the DAO:

```kotlin
// Example RowMapper implementation in AccountDao.kt
class CustomerMapper : RowMapper<Customer> {
    override fun map(rs: ResultSet, ctx: StatementContext): Customer = Customer(
        id        = rs.getLong("id"),
        firstName = rs.getString("first_name"),
        lastName  = rs.getString("last_name"),
        email     = rs.getString("email"),
        phone     = rs.getString("phone"),
        status    = rs.getString("status"),
        createdAt = rs.getObject("created_at", LocalDateTime::class.java),
        updatedAt = rs.getObject("updated_at", LocalDateTime::class.java)
    )
}

// Registering on DAO:
@RegisterRowMapper(CustomerMapper::class)
interface CustomerDao { ... }
```

## 3. Registering JDBI in Dropwizard

To set up JDBI inside your Dropwizard application, use `JdbiFactory` and install the `SqlObjectPlugin` to enable annotation support:

```kotlin
// In Application.run()
override fun run(configuration: AccountConfiguration, environment: Environment) {
    val factory = JdbiFactory()
    val jdbi = factory.build(environment, configuration.database, "mysql").apply {
        // Enable SQL Object API support
        installPlugin(SqlObjectPlugin()) 
    }

    // Generate DAO instances
    val accountDao = jdbi.onDemand(AccountDao::class.java)
    val customerDao = jdbi.onDemand(CustomerDao::class.java)
}
```

## 4. DB Health Checks

We verify that the MySQL server is available by registering a database health check that executes a simple check query:

```kotlin
// Example from DatabaseHealthCheck.kt
class DatabaseHealthCheck(private val jdbi: Jdbi) : HealthCheck() {
    override fun check(): Result {
        return try {
            jdbi.withHandle<Unit, Exception> { handle ->
                handle.execute("SELECT 1")
            }
            Result.healthy()
        } catch (e: Exception) {
            Result.unhealthy("MySQL is down: ${e.message}")
        }
    }
}
```
